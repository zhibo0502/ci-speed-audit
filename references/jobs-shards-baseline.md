# Job 拆分、Shard 负载均衡与回归基线

本文件是 `SKILL.md` 的按需参考（见「按需加载的参考文档」表）：当最慢 job / shard 硬门禁越线、需要拆分或均衡 shard 分片、或要在优化收尾建立防回归基线时读取。所有判定默认基于最近 **150 次** CI 运行的耗时数据；历史运行不足 150 次时按 `platform-adapters.md` 建临时基线并标明样本量。

## 1. 识别与拆分过大的 Job

**识别（以 150 次运行数据为依据）**：

1. 按最慢 job `< 35s` 硬门禁逐 job 对比 p50 与 p95，凡硬门禁越线或明显拖慢端到端关键路径（端到端 p50 `≥ 1m` / p95 `≥ 2m`）者即候选过大 job。
2. 拆解该 job 内部耗时：若 `running` 内串行执行了彼此无依赖的步骤，或单个测试文件本身 `> 20s`，即为可拆分信号（`setup` 占大头不是拆分理由——拆成多 job 只会重复克隆与装依赖，应回 setup 桶治理）。
3. 校验是否有任何必需 job 等待另一个 job——过大 job 常因把本可并行步骤挤在同一 runner 里造成端到端延迟。

**拆分判据（满足任一条即应拆分）与示例**：

- `running` 串行且步骤间无依赖 → 例如一个 job 同时串跑 `lint` + `typecheck` + `tests`，拆成并行 job 后各自的 `running` 并行执行，消除共用 runner 内的串行执行；反之，仅几秒的零散小校验应反向合并进一个 job（fold small checks into one job），避免重复启动成本。
- `running` 内单 job / shard 硬门禁越线 → 例如某测试 job p95 `45s`，按历史文件耗时均衡拆为 2 个 shard、每 shard 配独立 throwaway DB，使单 shard `< 30s`。
- 单文件单体耗时 `> 20s` → 例如 `e2e/login.spec.ts` 单跑 `25s`，必须先把其中的用例组拆到更小粒度文件，再将拆分后的文件按记录耗时参与 shard 均衡，不再让单文件成为 shard 下限。
- 关键路径被串行依赖拉长 → 例如 `tests` 串行等待 `build`、或报告步骤排在必需 job 前面，拆开后让 `lint` / `typecheck` / `build` / `tests` 全部并行启动，保证无任何必需 job 等待另一个 job（no required job waits on another）。
- 拆分前后必须保留完整性校验（prove all files ran）与硬门禁，防止拆出静默漏跑或 job 超预算不判红 FAIL 的“伪拆分”。

## 2. 用历史文件耗时做 shard 分片负载均衡

**做法**：

1. **收集基准耗时**：从最近 150 次运行（或临时基线有效样本）中提取每个测试文件的实测耗时（按测试执行器报告汇总，JS/TS 默认 `bun test`），形成“文件 → 耗时”清单；无历史数据的新文件先按该文件同类测试的中位数估算。
2. **按目标 shard 数做装箱分配**：以每个 shard `< 30s` 硬门禁为界，用贪心/装箱思路把文件从大到小依次放入当前总耗时最小的 shard，使各 shard 预估总耗时尽量接近；单文件 `> 20s` 的先按第 1 节判据拆小再参与分配。
3. **固定映射并留痕**：把 shard 分片映射写入 CI 配置或生成物，保证同一 commit 的重跑 shard 分片结果一致；同时保留“所有文件必须被分配到某个 shard”的完整性断言（prove all files ran）。
4. **周期再均衡**：测试文件增删或耗时漂移（例如某文件变慢 `> 20%`）后，重新跑步骤 1–3 更新映射，而不是长期沿用旧 shard 分片。

**均衡前后对比判据**：

- **shard 间总耗时方差**：均衡后各 shard 的 p50 总耗时应显著收敛，最慢 shard 与最快 shard 的差距（拖尾差）应明显小于均衡前，目标是最慢 shard `< 30s`。
- **端到端总耗时与 `running` 桶 p50 与 p95**：若均衡后最慢 shard 降了但端到端总耗时未改善，说明瓶颈在 `setup` 或 `waiting`（见 `bucket-diagnostics.md`）；若 `running` 桶本身未改善，说明关键路径转移到了其他并行 job（如 `build` / `typecheck`），按第 1 节继续拆分。
- **worker 利用率**：均衡后各 shard 的 CPU/线程利用率应更接近且接近饱和；若仍出现“个别 shard 拖尾但利用率不高”，回到 `bucket-diagnostics.md` 的常见误判定位排查锁竞争或共享资源串行。
- **完整性零漏跑**：均衡前后都必须证明 100% 测试文件已执行；若重新进行 shard 分片导致文件数对不上，即判本次均衡 FAIL，回退到上一版映射。

## 3. 用最近 150 次运行建立各桶耗时回归基线

**建立回归基线（4 步）**：

1. **区分触发口径并清洗样本**：仅在建立**回归基线**时，从最近 150 次运行中剔除被新提交取代而取消（superseded）或因前置失败提前终止的运行（初始瓶颈审计须保留这些样本，否则抹掉排队证据），并将 **PR 运行（筛选子集）** 与 **merge queue 运行（全量套件）** 分开建线，避免两类分布混算扭曲回归基线。
2. **分桶固化关键分位**：分别计算并记录 `waiting`、`setup`、`running`（含最慢 job 与最慢 shard）及端到端总耗时的 **p50 与 p95**，同步记录 PR 缓存命中率。
3. **绑定上下文元数据**：回归基线快照必须附带统计窗口起止时间、有效样本数、回归基线 commit、runner 规格、缓存键方案与工具链锁定版本（如 Bun exact canary），确保后续对比同口径。
4. **受控刷新而非基线自动漂移**：仅在优化 PR 合入并跑稳后刷新回归基线并留存上一版对照；禁止用“变慢后的滚动均值”自动覆盖回归基线，防止缓慢退化被正常化。

**回归硬门禁与分位诊断预警判据**：

- **端到端 PASS 未达成（150 次分位总目标 FAIL）**：PR 端到端 p50 `≥ 1m` 或 p95 `≥ 2m` 即视为端到端 PASS 未达成（FAIL），是唯一的端到端综合判定。
- **硬门禁越线（单次 job 执行判红 FAIL）**：仅限单次 CI job 执行预算——默认 Lint `≥ 1s`、Format `≥ 1s`、Typecheck / Build `≥ 5s`、单 shard `≥ 30s`、最慢 job `≥ 35s`（JS/TS 对应 `bun lint` / `bun fmt` / `bun check` / `bun test`；若仓库按 `budgets-and-checklist.md` 经实测重定并固化了单项阈值，则以重定阈值为准）——越线即直接判红 FAIL，不得放宽超时或加重试绕过；`waiting`/`setup`/缓存命中率的分位诊断目标未达标按 `bucket-diagnostics.md` 及下述分位诊断预警判据排查，不单独判红。
- **相对回归基线漂移（未越线即分位诊断预警）**：滚动窗口（如最近 20–30 次有效运行）相对 150 次基线出现任一桶 p50 上涨 `> 15%` 或 p95 上涨 `> 20%`，即使尚未触及硬门禁，也立刻触发分位诊断预警并按对应桶排查。
- **尾部发散（分位诊断预警）**：p50 基本持平但 p95 明显拉宽（如 `p95 − p50` 差值较回归基线扩大 `> 30%`），优先排查 `waiting` 并发排队尖峰、`setup` 缓存未命中（冷缓存）/无效命中或单个测试文件膨胀（`> 20s`）。
- **单点抖动 vs 真回归**：单次异常先记录不改回归基线；若连续多次硬门禁越线或滚动窗口 p95 抬升，则判为真回归，按回归基线元数据对照依赖、缓存键、runner 或新增测试文件定位引入 commit，修复后须给出指标回落到回归基线以内的校验结果。
